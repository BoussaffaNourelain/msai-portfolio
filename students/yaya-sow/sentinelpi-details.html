Raspberry Pi 4 + OpenWrt · isolated student security lab

What We Are Doing in the SentinelPi Project

We are building a small, realistic cybersecurity network around a Raspberry Pi 4. The Pi becomes the central security appliance: it routes traffic, separates the lab from the upstream network, provides network services, watches traffic with an IDS, keeps security evidence, and supports controlled red-team and blue-team exercises.

Safety rule: This project is designed for an isolated educational lab. Keep the lab physically and logically separated from production or organizational networks, and perform attack exercises only against systems you are authorized to test.

SentinelPi

Raspberry Pi 4 running OpenWrt. It becomes the gateway, firewall/NAT device, DHCP/DNS service, IDS/IPS sensor, and logging point.

Attacker + Victim

The attacker is an authorized lab VM. The victim is an intentionally vulnerable test VM. They give us realistic traffic to detect and investigate.

Monitor + Evidence

A separate monitoring VM stores or views security information. We also preserve packet captures, logs, reports, tests, and documentation.

Lab network plan

SentinelPi LAN gateway: 10.10.10.1 · LAN: 10.10.10.0/24 · DHCP pool: 10.10.10.100–200 · Attacker: 10.10.10.50 · Victim: 10.10.10.100 · Monitor/SIEM: 10.10.10.90.

The original guide defines a strict rhythm for every phase: build something, verify it, test it, document the result, and only then continue. The explanations below preserve the source's phase order and cover all 63 phases, from Phase 0 through Phase 62.

Install OpenWrt (Download & Verify)

Main location(s): ADMIN-PC
What this phase is doing
OpenWrt is the router firmware that turns the Pi into a firewall/router. Verifying the checksum proves the file wasn't corrupted or tampered with during download — never skip this on a security appliance.
Step-by-step explanation
  1. Go to the official OpenWrt downloads site and find the image for 'Raspberry Pi 4 (bcm27xx / bcm2711)'.Complete this before moving forward so the next phase starts from a known, working state.
  2. Download the .img.gz file and the checksum file (sha256sums) published alongside it on the same official site.The purpose is to prove the downloaded firmware is the exact file you intended to use, rather than a corrupted or altered copy.
  3. Compute the SHA256 hash of the file you downloaded and compare it character-by-character against the official value.The purpose is to prove the downloaded firmware is the exact file you intended to use, rather than a corrupted or altered copy.
Checkpoint: The hash you compute matches the official published checksum exactly.
Important: If the checksum does not match, delete the file and download it again. Do not flash a file with a mismatched hash.
